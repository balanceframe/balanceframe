# ADR 0001: Immutable purchase decisions and explicit Spend Session completion

**Status:** Accepted

## Context

A purchase check must distinguish envelope funding from payment-account readiness before any ledger write. Temporary reservations, commitments, and proposed cart items affect shared spendability, but are not Actual transactions. A saved cart can later become a manually entered Actual transaction or split; retrying an uncertain external write could duplicate a financial obligation.

## Decision

- The Rust financial core evaluates normalized, versioned snapshots and policies into an immutable Decision Card. It owns checked money, joint cart analysis, funding alternatives, optional-first trim, reasons, hashes, and postconditions. TypeScript normalizes Actual data and holds authorization, scoped projection, persistence, and execution. No model result is financial authority.
- A Spend Session stores item-level price and category intent, quantities, priorities, adjustments, warnings, and expiry. Saving a new version invalidates its uninitiated completion approvals. Outside prices record a source, observation time, estimate flag, and store only when known.
- Prospective reservations and commitments live in the workflow claim set. They never create an Actual transaction. Policy decides whether they block or inform. Different category/account scopes of the same session version have distinct economic effect identities and retain their original source-obligation identity for exact matching; an upgrade migrates older unsuffixed scopes and advances the claim-set revision to invalidate stale decisions. A completion Card excludes active claims originating from that exact version while considering other claims; when an active completion covers the same actor's exact category/account amount, the effective claim set uses the completion hold once, leaving the separate prospective record active until verified manual-parent evidence atomically consumes it. An unsuccessful pre-write completion does not erase the originating hold. Verification makes the entire saved session terminal.
- The user proposes an exact, one-account debit and optional category splits from a currently funded Card; the workflow persists the immutable payload, claim, policy-dependent cooldown, approval requirements, and audit. Approval and execution are separate authorized actions. The approving peer needs only exact debit scopes; private Card re-evaluation uses the saved session owner's grants and never exposes the underlying cart to that peer. Before execution, the service re-evaluates current snapshot, policy, claims, session version, and complete Card material hash and requires both initiation and confirmation grants before Actual is called.
- Execution persists a one-shot write intent before calling the mutation-only Actual connector. It never retries an uncertain write. The connector synchronizes, checks for matching imported candidates and existing parent IDs, writes at most once, synchronizes and re-reads the exact parent and splits, then reports verified evidence. A certain imported-candidate preflight abort releases the unused hold for reconciliation review; any attempted or uncertain write retains the initiated hold. An intervening saved-cart edit or cancellation cannot discard verified evidence for a write already in progress. Later imports can link to an already verified manual parent without producing a second debit.
- Client idempotency keys identify the actor, budget, saved-session version, and exact client creation intent; replay resolves the existing proposal/claim before a new evaluation observes its own hold. Reusing a key with different intent is rejected. The persisted claim and proposal remain the concurrency and audit source of truth.

## Consequences

BalanceFrame does not maintain a parallel transaction ledger or perform silent matching/merging. Incomplete or ambiguous ledger evidence produces an insufficient-data or human-review result, not a confident recommendation; reconciling an uncertain write requires complete account and transaction coverage before declaring its manual parent unambiguous. A verified session is terminal; another purchase requires a new session, not a new version of the completed cart. Scoped prospective effects retain separate identifiers and an authenticated source-obligation link; only exact matching authoritative obligation evidence nets them as one charge. Authorization projects only granted account/category details, including for a coapprover reviewing another actor's exact completion debit without seeing that actor's cart.
