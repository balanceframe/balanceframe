# ADR 0002: Owned disposable feature-scenario demos

**Status:** Accepted

## Context

BalanceFrame needs reproducible user stories and local verification for purchase Cards, account routing, Spend Sessions, claims, approval, and reconciliation. Those paths depend on the Rust native addon, Actual's server and budget state, SQLite workflow authorization, and Better Auth. Browser-only fixture playback or a static screenshot cannot exercise those boundaries. A long-lived shared budget would mix unrelated evidence and risk financial mutations outside the demo.

## Decision

- Maintain one checked, versioned catalog of 40 independently loadable fictional scenarios: the original 29 spending stories plus three governance and eight merchant stories. The same materialization, Actual seeder, authenticated workflow initializer, protected manifest and event recipes drive the CLI's live acceptance cases and the user-facing demo. Logical fixture IDs are mapped to the exact IDs returned by the freshly seeded Actual budget. A scenario is ready only after its authenticated read succeeds with the native addon present; no canned financial analysis substitutes for that read.
- Each run owns a private parent root, an Actual process/data directory, a production Nuxt child, an isolated auth/workflow/config store, and generated credentials. The supervisor stages a replacement workspace before publishing a reset, drains in-flight financial and identity-bearing requests, increments a generation, invalidates old control sessions, and removes only registered owned paths. Loading failure leaves a visible fail-closed selector rather than a fabricated financial result.
- A bounded HTTP supervisor exposes only catalog, state, generation-bound entry, and explicit load/reset/persona/event controls. Host and Origin are checked; POST controls require a signed, expiring cookie and CSRF proof. The private child accepts setup only with its protected manifest and internal header. Its demo boundary denies ordinary setup/auth/connection writes and disallowed financial operations, even if the proxy is bypassed. The demo never accepts an arbitrary URL, shell command, external Actual instance, bank connector, or model endpoint.
- Demo-only Better Auth sign-in uses a finite higher limit (20 per 10 seconds) because startup signs in three fictional actors from one private loopback address; public sign-in remains denied by the child boundary. In-flight persona and `/demo` authentication join the reset drain, and late authentication responses cannot set cookies for a replaced generation.
- Active human personas are real fictional Better Auth users with explicit workflow membership and resource capabilities; pending invitations have no fabricated actor/session. Invitation redemption and rejoin use normal handlers, with rejoin creating a new membership rather than restoring old grants. The assistant is a real bounded agent/delegation/API-key principal and never a human persona. Development authentication bypass is disabled. Entry into an ordinary application page is projected for the current persona; private IDs and amounts are not sent to another persona. The selector and banner disclose that data are fictional and resets affect a shared instance.
- `scenarios verify --all` requires successful named assertions for every independently approved story ID and mutually exclusive behavior branch; a zero Vitest exit, catalog count or missing/skipped record cannot establish coverage. Each load uses a real isolated Actual/Nuxt workspace and emits sanitized JSON evidence. Four named native/service fault contracts remain separate because ambiguous bank receipts, duplicate source-coverage assertions, identity overlap and interrupted connector responses cannot honestly be manufactured as ordinary Actual ledger events.
- Native-rule intent binds the complete current Actual source graph, including generated baseline resources and exact published merchant evidence. Owner proposal/execution and independent reviewer approval/full-read grants are finite and operation-specific; reviewers receive no budget-wide full-read, execution or control grants. Newly imported transactions and created rules extend only validated exact native-ID scopes through normal owner grant handlers.
- Merchant research uses an explicitly selected, private-manifest-bound closed fixture provider through the existing real coordinator/policy/cache/quota machinery. It has no network transport, paid key read, caller-chosen provider URL or live fallback. Fixture provenance and modeled tariff are disclosed. Its bounded clock affects research only, not source freshness or human proof. Content admission remains current-authority gated; content-free held retirement validates original-generation private files and cannot mutate a successor.
- Held release/cancel controls validate current owner, origin, CSRF, proof and generation without draining their own outstanding research request. Reset/shutdown cancels held fixture work before draining. Governance metadata probes remain bounded local tooling with normal session/key admission, real governance authorization before and after native Actual metadata lookup, and no financial/history disclosure; no production resource-enumeration API is introduced.
- Complete Review benchmarks reuse the owned Actual/Nuxt runtime, normal fictional Better Auth identity, the canonical sparse merchant scenario, and exact native-ID source/view grants. Both writer and independent published SDK captures must preserve baseline native ledger facts, generated rows and every account balance against the exact generated delta; admitted source size must be complete. An ordinary read-only budget summary refreshes the web SDK without populating Review. First physical Sync must produce the mapped canonical target queue and item identity/money before two warmups and twenty same-runtime repetitions. Timing ends only after correlated successful Sync, authorized queue/category reads, and the rendered fixture item with enabled Sync. Observed setup/inter-epoch page errors remain failures; known dataset-deadline interruptions are censored. There is no invented full-UI performance threshold.
- SDK snapshot duplicate observations use a transient tuple index, built only when an imported row needs duplicate evidence. The Review layout independently refreshes budget summary during page initialization, so a per-imported-row full-history scan blocks ordinary requests at representative source sizes. Nested native-field maps retain the earliest two distinct IDs, preserving strict account/date/amount/payee equality, first-different-ID evidence order and manual-row candidates without changing financial calculations or transfer matching.
- Benchmark reports and screenshots are exclusive private artifacts. Linux memory observations cover only the owned Actual/web entry processes and report approximate sampled RSS and lifetime high-water deltas, not whole-process-tree or exact physical memory. Cancellation propagates to setup HTTP and scoped SDK transport, owned teardown is awaited, and uncertain client cleanup retains the private root and prevents starting another dataset.
- SDK ownership begins with initial fixture seeding, including partial initialization failure. Shutdown must be attempted before returning or preserving the original failure. Unproven shutdown stops owned servers but retains the affected private root; the loader and benchmark propagate uncertainty, and the demo refuses successor loads with `DEMO_CLEANUP_UNPROVEN` until process restart. Shutdown-proven ordinary seed failures remain recoverable.
- Current-item money comes from the authorized Review DTO's `evidence.money` and is checked against both canonical fixture and native SDK facts. Actual display preferences do not define the connector's configured ledger currency and are not a prerequisite for these disposable measurements.
- A clean short sampling run keeps its verified queue stability, null p95 and unproven reference status without inventing a failure. Known cancellation during teardown finalizes every earlier status; cleanup uncertainty takes precedence. Chromium spawn errors reject acquisition through the same awaited SDK/store/server cleanup, without signaling an absent PID.
- Pin the existing `@actual-app/api@26.10.0` dependency with a one-line pnpm patch: grouped transaction matching uses `rows.flatMap(...)` instead of history-sized function-argument expansion. The public SDK's real 250k-row readback reproduced the upstream stack overflow before this change and preserves every requested transaction and exact account balance afterward. All SDK consumers use the same locked patch; no per-caller truncation or chunked-query workaround is introduced. Revalidate the regression and remove the patch when a pinned upstream version fixes this path.
- Scaled benchmark preparation uses the SDK's supported `sync-reset` only after validating the loaded disposable cloud budget ID and exact writer financial facts. It compacts sync/deferred/tombstoned history and republishes under a new sync group; the cloud budget, live native IDs, financial fields and balances remain invariant and are verified through a fresh SDK directory. All later readers use the returned group. The private non-public merchant runner can reconnect only in its exact selected space through normal owner reauthentication and the existing unchanged-budget connection handler; public/shared-demo connection writes stay blocked. Default server upload and SDK ZIP safety limits remain unchanged.
- Governance grant preparation reuses the bounded static SQLite statement shapes per database instance. Rebuilding native statements for every exact grant exhausted the owned job's 12 GiB operational cap during scaled fixture preparation. Only compiled SQL is retained: identity, membership, time, revocation and restrictions are queried afresh on each call, and the per-grant write/readback/audit transaction is unchanged. The statement cache neither grants broader authority nor caches an authorization decision.

## Consequences

A demo requires the source-built native addon, Nuxt bundle, and pinned local Actual runtime; it is not deployable as static browser files. A shared instance is intentionally mutable by its fictional users and must be reset between independent stories. By default the supervisor listens on loopback; non-loopback exposure requires an exact HTTPS public origin and a trusted TLS reverse proxy, plus disposable state and network restrictions. A verified completion writes only to that run's throwaway Actual budget. Normal shutdown removes private secrets and manifests; an unproven SDK shutdown deliberately retains its 0700 workspace and 0600 manifest. Stop the owning process before inspecting or removing that retained disposable data. Fixture readiness is evidence-based: missing or expired attestations remain insufficient data rather than becoming ready merely because a scenario was selected.

## Expansion verification

The source application was operated at `http://127.0.0.1:3003` against separately loaded disposable Actual budgets, using real fictional Better Auth principals with development bypass disabled:

- Governance: Checking name/existence grants, separate invitation redemption and revoked/rejoined membership periods, bounded assistant metadata followed by same-key `401` after revocation. Coapproval recorded two distinct humans for the $26 debit ($8/$5/$13 splits) without execution; non-owner audit filters returned their respective attributed rows, withheld financial IDs, and allowed cross-actor access. The owner retained cross-actor access; the restricted viewer had no audit controls.
- Local merchant evidence: the $346.07 Aster holdout had three real category observations; the one-observation and empty-identity variants remained insufficient. Selecting the non-suggested Other category enabled confirmation without submitting it. Alias accept/reject persisted versions 1/2 without Actual edits. Calendar-backed recurrence confirmation appeared on Dashboard; rejection and unknown-calendar fallback were observed separately.
- Native rules: scoped reviewers with empty transaction queues opened the normal proposal modal, approved independently without execution rights, and the freshly confirmed owner executed one rule. Normal Rules showed the exact payee/category IDs; the declared future-import control succeeded. A separate fresh proposal, source change and authorized execution attempt returned `409 PRECONDITION_FAILED` with zero Actual rules.
- Closed research: independent exact-preview consent was required before a fixture result; expiry removed cache eligibility while local support remained three observations. The separate outage returned `failed/unavailable` with modeled uncertain billing and no automatic retry. A held dispatch was released from another browser tab without deadlock and withheld its late result as `stale_source`. Disabling the actual space policy then rejected an already-consented preview as `unauthorized/not_dispatched`.
- Payment preferences: the funded-purchase owner opened `/liquidity/settings` with ordinary session identity and saw the eligible form before reauthentication. Groceries and Household Checking left Save disabled until `CONFIRM`; disposable reauthentication and the normal preference PUT both returned `200`. The saved route retained version 1 and expiry `2026-10-07T23:02:00.000Z`, cleared confirmation and disabled Save again. A normal page reload and unproved GET retained the exact saved route with `canManage: true`.

Browser page errors and warning/error console entries were empty; observed browser request destinations were loopback only. Exact cache-reuse, daily/monthly quota, deletion-fence, reset-generation and Actual-only future-import readback assertions belong to the published local acceptance command; the browser observations above do not substitute for those checks.
